# Ecommerce demo on Google Cloud

This folder holds everything needed to run the Ecommerce backend as a public demo on Google Cloud, and to redeploy it on
every push to `master`. The Vue frontend (`ecommerce-frontend` repository) is published separately to Firebase Hosting;
see its `deploy/README.md`.

```
GitHub Actions  --(keyless, Workload Identity Federation)-->  Google Cloud project ilandeka-demos (shared with booking
  test + build image                                          and Royale League)
  deploy on push to master                                     Artifact Registry   container images (repo "demo")
                                                               Cloud Run service   ecommerce-api   (this repository)
                                                               Cloud Run job       ecommerce-demo-reset (after every deploy, nightly)
                                                               Cloud SQL           demo-pg, PostgreSQL 16, database "ecommerce"
                                                               Secret Manager      database password, JWT key, admin code, Stripe, Gmail
                                                               Cloud Scheduler     nightly reset
                                                               Firebase Hosting    Vue frontend (other repository)

Browser --> https://ilandeka-ecommerce.web.app  (Hosting)  --calls-->  https://ecommerce-api-<project number>.europe-west1.run.app
Stripe  --> https://ecommerce-api-<project number>.europe-west1.run.app/api/payments/webhook
```

| File | Purpose |
| --- | --- |
| `gcp/config.env` | Project id, project number, frontend site and feature switches. While the first three are empty, pushes to `master` only build and test. |
| `gcp/bootstrap.sh` | One-time (and safe to repeat) Google Cloud setup. Also the sub-commands `stripe`, `schedule` and `mail`. |
| `../.github/workflows/ci-cd.yml` | Tests and a Docker build on every pull request; tests, image build, deploy and checks on `master`. |

## Cost

About 13 USD (or EUR) per month on top of the booking and Royale League demos: one Cloud Run instance that is always
running (1 vCPU, 1 GiB), so a visitor never waits for a cold start of about 15 seconds. The database costs nothing extra:
it is another database on the shared `demo-pg` instance. Firebase Hosting, Secret Manager and Artifact Registry stay inside
their free tiers; Cloud Scheduler gives three jobs per billing account for free and this is the fourth (about 0.10 USD per
month). Stripe in test mode is free.

To save the 13: set `CLOUD_RUN_MIN_INSTANCES=0` in `gcp/config.env`. The service then scales to zero and the first visitor
after a quiet period waits about 15 seconds.

## Credentials

No secret is committed. Everything secret lives only in Secret Manager: the database password, the JWT signing key and the
admin registration code (all generated by `bootstrap.sh`), the Stripe test secret key and webhook signing secret (stored
with `bootstrap.sh stripe`) and the Gmail app password (copied from the booking demo, or stored with `bootstrap.sh mail`).
The non-secret values next to them are in `gcp/config.env`, with a switch per feature (Stripe, email).

`application-dev.properties` only has local-development values (a throw-away database on your machine, placeholders for
Stripe and email). The older `application-prod.properties` (AWS Elastic Beanstalk and MySQL) was replaced by
`application-production.properties`, which has no values of its own: Cloud Run injects every one of them.

## One-time setup

The booking demo's `bootstrap.sh` must have been run before (it created the project, the database server, the registry and
the keyless GitHub access). Everything below uses the same project.

1. **Stripe test keys.** In the [Stripe Dashboard](https://dashboard.stripe.com/test/apikeys), with *Test mode* on:
   * copy the *Publishable key* (`pk_test_...`) and the *Secret key* (`sk_test_...`);
   * *Developers, Webhooks, Add endpoint*: URL `https://ecommerce-api-608005285168.europe-west1.run.app/api/payments/webhook`,
     events `payment_intent.succeeded`, `payment_intent.payment_failed` and `charge.refunded`. Copy the endpoint's
     *Signing secret* (`whsec_...`). The address exists before the first deploy, so this can be done now.
2. **Open Cloud Shell** at <https://shell.cloud.google.com> and upload `deploy/gcp/bootstrap.sh` (three-dot menu,
   *Upload*; it drops the executable bit).
3. **Run the setup:**

   ```bash
   chmod +x bootstrap.sh
   ./bootstrap.sh
   ```

   It takes a minute or two. It creates the runtime identity `ecommerce-api`, the database `ecommerce` with its user, the
   secrets (database password, JWT key, admin code; the Gmail app password is copied from the booking demo), the keyless
   link for the two repositories (`Ecommerce` and `ecommerce-frontend`) and the Hosting site `ilandeka-ecommerce`.
4. **Store the Stripe keys:**

   ```bash
   ./bootstrap.sh stripe
   ```

   It asks for the secret key and the webhook signing secret with hidden input and refuses live keys (`sk_live_...`).
5. **Switch Stripe on.** Set `STRIPE_ENABLED=true` in `gcp/config.env` (in the pull request, or in a follow-up one).
   The secrets must exist before a deploy runs with the switch on, otherwise the Cloud Run deploy fails (the running
   version keeps serving).
6. **First deploy.** Merge the backend pull request to `master`. The *CI/CD* workflow runs the tests, builds and pushes the
   image, deploys `ecommerce-api` and `ecommerce-demo-reset`, waits for `/health`, resets the demo data and then checks
   the product list, CORS for the Hosting site and that the Stripe webhook route is reachable. The run summary shows the
   API and webhook addresses.
7. **Frontend.** Merge the frontend pull request (it needs the publishable key in its `deploy/gcp/config.env`).
8. **Scheduled reset.** After the first successful deploy, run `./bootstrap.sh schedule` in Cloud Shell. It adds the
   nightly reset at 03:30 (Europe/Zagreb). Check it once with:

   ```bash
   gcloud scheduler jobs run ecommerce-demo-reset --location=europe-west1
   ```

## What visitors get

* Seeded demo data (`DataLoader`): nine products and two accounts, thrown away and re-created after every deploy and every
  night at 03:30 (`DemoResetRunner`, profile `demo-reset`, run as the Cloud Run job `ecommerce-demo-reset`):
  * customer `test@test.com` / `test`
  * admin `admin@admin.com` / `test` (adds and edits products, uploads product pictures)
  * the frontend shows both on the sign-in page and offers a one-click fill.
* Checkout runs against Stripe's **test mode**: card `4242 4242 4242 4242`, any future expiry, any CVC, any postal code. No
  real money moves. After a successful payment Stripe calls the webhook and the order turns to *Paid* a moment later.
* Password reset sends a real email through Gmail (`MAIL_ACCOUNT_ENABLED=true`) with a link to the Hosting site.
* Admin accounts can only be created with the admin code (`POST /api/auth/register/admin`). The code is the secret
  `ecommerce-admin-code`; read it in the Secret Manager console when you need it.

### Known limits of the demo

* **Product pictures uploaded by the admin are stored on the instance's disk** (`uploads/products`), which Cloud Run does
  not keep. They disappear when the instance restarts, on every deploy and at the nightly reset. The seeded products use
  the default picture. Keeping them would need a Cloud Storage bucket behind `ImageService`.
* **One instance only.** Signed-out access tokens are remembered in memory (`TokenBlacklistService`), so the service is
  capped at one instance (`--max-instances 1`). At demo traffic one instance is plenty.
* Orders and payments made in Stripe's test mode stay in your Stripe test dashboard after the database is reset.
* The demo accounts are shared by every visitor: anybody can change their password (*Profile, change password*) or edit the
  catalogue as the admin. The nightly reset puts everything back.

## Everyday operations

* **Redeploy:** push to `master`, or run the workflow by hand (*Actions, CI/CD, Run workflow*).
  **Roll back:** Cloud Run, *ecommerce-api*, *Revisions*, send 100% of the traffic to the previous revision.
* **Logs:** Cloud Run, *ecommerce-api*, *Logs* (the reset job has its own under *Jobs*).
* **Reset the data now:** `gcloud run jobs execute ecommerce-demo-reset --region=europe-west1 --wait`
* **Rotate a secret:** store the new value (`./bootstrap.sh stripe` or `mail`), then re-run the latest *CI/CD* run on `master`
  (Cloud Run reads `latest` when an instance starts). To rotate the JWT key, add a new version of `ecommerce-jwt-secret`
  and redeploy; everybody is signed out once.
* **Custom domain for the frontend:** set `ECOMMERCE_PUBLIC_URL` in `gcp/config.env` so the API accepts calls from it.
* **Tear everything down:** delete the pieces of this demo (the Cloud Run service and job, the database `ecommerce` on
  `demo-pg`, the `ecommerce-*` secrets, the Hosting site). `gcloud projects delete ilandeka-demos` would remove the other
  demos too.

## Local development

The tests and the `dev` profile need a PostgreSQL database; the workspace's `compose.yaml` starts one (port 5434,
database, user and password `ecommerce`):

```bash
docker compose up -d                                 # from the folder above the repositories
./mvnw -B -ntp verify                                # build + tests, same as CI
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev   # http://localhost:8080
docker build --platform linux/amd64 .                # CI checks this on every pull request; Cloud Run runs amd64
```

The `dev` profile reads Stripe and email settings from `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `EMAIL_USERNAME` and
`EMAIL_PASSWORD` (placeholders otherwise). Use Stripe test keys, and `stripe listen --forward-to
localhost:8080/api/payments/webhook` to deliver webhooks to your machine.

## How it is locked down

* No service account keys exist. GitHub Actions exchanges its short-lived identity token for access to the `gh-deployer`
  service account, and only for workflows of your own repositories that run on `main` or `master`. Pull requests get no
  access to Google Cloud at all.
* `gh-deployer` may deploy Cloud Run services and jobs, push images and deploy to Firebase Hosting. It cannot read the
  secrets or the database.
* `ecommerce-api` (what the running service uses) may connect to Cloud SQL and read its own secrets, nothing else.
* The database accepts no direct connections from the internet; the service reaches it through the Cloud SQL connector,
  which checks IAM first.
* The API accepts browser calls only from the Hosting site (`APP_CORS_ALLOWED_ORIGINS`), and refuses to start without a
  JWT key. Stripe webhooks are public by necessity (`/api/payments/webhook`) but are only accepted with a valid
  `Stripe-Signature`.
* The demo reset is a Cloud Run *job* (started by the workflow after each deploy and by Cloud Scheduler at night), not an
  HTTP endpoint, so there is nothing on the public API that can wipe data.
* `bootstrap.sh stripe` refuses live Stripe keys.

## Troubleshooting

* **The deploy job is skipped.** `gcp/config.env` still has empty values.
* **`Permission 'iam.serviceAccounts.getAccessToken' denied` or `rejected by the attribute condition` in the deploy job.**
  The workflow did not run on `main` or `master`, or the repository is not allowed to deploy: run `./bootstrap.sh` again
  (repository names are case-sensitive: `Ecommerce`, `ecommerce-frontend`).
* **The deploy fails with a secret that is not found or cannot be accessed** (for example `ecommerce-stripe-secret-key`). A
  switch in `gcp/config.env` is on but its secret was never stored. Run the matching `bootstrap.sh` sub-command, then
  re-run the workflow, or turn the switch off again.
* **`gcloud run deploy` says the container failed to start.** Open the *ecommerce-api* logs. Typical causes: a secret or the
  Cloud SQL connection is missing (run `bootstrap.sh` again, it repairs both), or `application-production.properties` needs
  a variable the workflow does not set.
* **`permission denied for schema public` in the logs.** PostgreSQL 15+ no longer lets ordinary users create tables in
  `public` unless they own the database. Give the app user ownership once:

  ```bash
  gcloud sql users set-password postgres --instance=demo-pg --prompt-for-password
  gcloud sql connect demo-pg --user=postgres --database=ecommerce
  ```

  and in the SQL prompt:

  ```sql
  GRANT ALL ON SCHEMA public TO ecommerce;
  ```

  (if that is refused, run `GRANT ecommerce TO postgres;` and `ALTER DATABASE ecommerce OWNER TO ecommerce;` instead), then
  redeploy.
* **An order stays *Pending* after a successful test payment.** Stripe's webhook did not arrive or was rejected. In the Stripe
  Dashboard (test mode), *Developers, Webhooks*, open the endpoint and look at the recent deliveries: `401/403` means the
  route is blocked (the workflow's last check would have failed), `400` or `500` with "Invalid webhook signature" in the
  *ecommerce-api* logs means the signing secret in Secret Manager is not the one of this endpoint (store it with
  `./bootstrap.sh stripe` and redeploy).
* **Checkout shows an error as soon as the payment form should appear.** `STRIPE_ENABLED` is `false`, or the frontend was built
  without `VITE_STRIPE_PUBLISHABLE_KEY` (see the frontend's `deploy/gcp/config.env`).
* **The browser shows a CORS error.** The Hosting address in the browser is not in `APP_CORS_ALLOWED_ORIGINS` (the web.app and
  firebaseapp.com addresses of `ECOMMERCE_SITE_ID`, plus `ECOMMERCE_PUBLIC_URL` when set).
* **Public access is refused (`allUsers`) during deploy.** The project sits inside a Google Cloud organization that restricts
  sharing to your own domain. A personal Gmail account does not have this limit; with a Workspace organization, relax the
  *Domain restricted sharing* policy for the project.
* **A request takes about 15 seconds.** That is a Spring Boot start. With `CLOUD_RUN_MIN_INSTANCES=1` it only happens right
  after a deploy or when Google restarts the instance.
